# freight-audit-lab

A portfolio project: a small, honest simulation of freight invoice audit and month-end
freight accruals, built on **synthetic data**. The full build spec is in `SPEC.md`.
Work through it one stage at a time.

The author is an accountant with a data science background. They must be able to explain
every line and every assumption in an interview, so clarity beats cleverness everywhere.

## Hard rules

1. **Synthetic or public data only.** Never add real company, client, carrier, or person
   data. Carrier names are invented (e.g. "Carrier A Freight"). The only public input allowed
   is an optional EIA weekly diesel CSV the author supplies. Every generated file lives under
   `data/` next to a `data/README.md` that says "SYNTHETIC DATA – generated by
   freight_audit_lab.generate".
2. **No ground-truth leakage.** Ground-truth labels and injection metadata are written only to
   `data/ground_truth/`. Only `freight_audit_lab/evaluate.py` and `freight_audit_lab/sweep.py`
   may read them. Normalization, re-rating, audit, and accrual code must never import or
   read them. There is a test that enforces this (see SPEC Stage 4).
3. **No look-ahead in accruals.** An accrual at month-end M may use only information
   available at M: invoices *received* on or before M, authorizations recorded on or before
   M, diesel prices published on or before M, and rate cards effective on the ship date.
4. **Everything configurable lives in `config.yaml`.** No magic numbers in code (rates,
   tolerances, error rates, seeds, dates, cost assumptions). Load the config once and pass it down.
5. **Reproducible.** One seed in `config.yaml` drives every random draw (use
   `numpy.random.default_rng(seed)` and pass the generator; never use global random state).
   Same config means byte-identical outputs.
6. **Label estimates.** Any number that is an estimate (accruals, review cost, recoverable
   dollars) is labeled "estimate" in column names, dashboard captions, and docs.
7. **Money.** Compute in floats, round to cents at the charge-line level with
   `round(x, 2)`, and compare money in tests with a $0.01 tolerance.
8. **Never invent results.** README, ASSUMPTIONS, and any doc that quotes a number must
   pull it from `outputs/summary.json` or other files in `outputs/`.

## Style

- Python 3.11+. Dependencies: pandas, numpy, pyyaml, pytest, streamlit, altair (ships with
  Streamlit). Don't add others without asking.
- Plain pandas and small functions with docstrings that give the *business* reason
  ("carriers price LTL per hundredweight, so...") as well as the mechanics.
- Flat package layout (no `src/`) so Streamlit Community Cloud can import it:
  `freight_audit_lab/` at repo root, `streamlit_app.py` at repo root, tests in `tests/`.
- Keep modules short. Prefer explicit column names over positional logic.

## Workflow

- Do **one SPEC stage per request**. At the end of a stage: run `pytest -q`, run the
  pipeline if it exists yet, print a 5-10 line summary of what changed and any key counts,
  and **stop**. Don't start the next stage unprompted.
- If the spec is ambiguous, choose the simplest reasonable option and log it in
  `ASSUMPTIONS.md` (one bullet: the assumption, why, and how to change it in config).
- If a spec requirement seems wrong or would take much longer than expected, say so and
  propose an alternative before building it.
- Commit at the end of each stage with a message like `stage 3: normalization layer`.
- `README.md`, `WALKTHROUGH.md` and `outputs/findings.md` are generated from `docs/*.template.md` and
  `outputs/summary.json` by the pipeline. Edit the templates, never the generated files.

## Commands

```bash
pip install -r requirements.txt
pytest -q
python -m freight_audit_lab.run          # full pipeline: generate -> ... -> outputs/
streamlit run streamlit_app.py
```
